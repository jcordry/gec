## Space Indexing

- Space Indexing

   - Indexes space so that we can perform queries without examining the whole set

   - The simplest would be just to store all the entities in a collection like a vector however once you get many entities this becomes difficult to search

- Space partitioning is a way of indexing space



---

## Uses

> Used by spatial databases to optimise spatial queries

> Allows effective handling of how far two points differ and if points fall within a region etc. Solutions : Grid, Z-Order, Quadtree, Octree etc.

> Games

- Collision detection

> View frustum culling of terrain data

---

## Space Indexing

- The simple method is to use a grid

   - We divide the area into a grid and assign entities to a bucket per cell (normally in a linked list)

   - For collisions we just look at surrounding cells

   - Does not work well with large differences in entity sizes

      - Leads to entities belonging to many cells and large memory use



---

## Space Partitioning

> Useful for reducing processing required for:

- Graphics rendering

- Collision detection

- Any spatial index question like "Is there any entity closer than x units?" or "How many entities are closer than x units?"

> Some types

- Quad and Oct trees

> Divide the space into fixed size areas (4 or 8)

- BSP and kd-Trees

   - Divide the space using planes into a binary tree

## Quadtree

- A quad tree divides each region into 4

   - We can then recursively divide each new region into 4

- The original method loops through all entities and creates the tree from them



<!-- Start of picture text -->
~N<br><!-- End of picture text -->

---

## Original

- The original quad tree has several features

   - Only leaf nodes contain entities

   - It has a maximum number of entities per leaf

- To add to the tree

   - Start with just a root node

   - Loop through all entities

      - Place the entity in the tree node at the lowest level

      - If the max entities per node is reached divide the area into four and place the entities in the correct quadrant.

         - We may need to do this a few times until there is less than the max number of entities per node

   - At the end go through the whole tree pruning leaf nodes that do not contain entities (for an adaptive quad tree)

---

## Original

> Setting a max number per node can cause problems if entities overlap

> so, subdividing the space does not reduce the number of entities per node

> Note: we could just hold one entity per leaf node

> Useful for image representation (per pixel)





Game Use

---

## For our uses

- For games we may want to use quad trees to

   1. Reduce the number of entities we attempt to render

   2. Reduce collision detection tests

- For 1) we could create a fixed quadtree at level load (or even in advance) just for non-dynamic entities

- Where we want to handle dynamic data:

   - Entities can move and so we need to be able to quickly insert them into the tree

   - We could do this dynamically with the traditional approach at run time, but it could be slow

---

## Game Use

- Requirements

   - We do not want to be doing dynamic tree building during our game loop if possible

   - We want to be able to specify a maximum tree depth

   - We may or may not be able to have a fixed size bucket for each cell (depends on the game) but we would like it to be fixed

   - Due to varying sizes of entities in a game we do not want to restrict ourselves to only storing entities in leaf nodes

   - We want to be able to quickly assemble a list of all entities within an area

- Note: experimentation is needed to find the most effective depth and bucket size

---

## Building the tree

> The first step is to build our fixed size tree

> We are going to need to define a node



---

## Tree Node

- Each node in our quad tree will need:

- A reference to 4 other nodes

   - Could be a pointer or index etc.

- A bucket of entities

   - You could create an interface class specifically to add into the quad tree or use an 'entity' base class.

   - What are the advantages of using an interface class?

      - We could add other items apart from just entities

      - Makes our tree more flexible and self-contained

      - *Entities being the smallest thing you wish to index

---

## Tree Node

> An initial structure struct Node {

Node *ne,*nw,*se,*sw; Bucket*entityBucket; };





---

## Tree Node

- The bucket itself (if not a fixed size) needs to be able to grow and shrink

   - When removing an item, we need to find it quickly

> A linked list is a possible choice



---

## Building

- We specify our start area of space e.g. 1000 wide (x) by 1000 high (y)

- We create a function that will take a region and break it into 4

- creating 4 new nodes

- We will call this function recursively until we have reached the maximum depth or our tree



---

## Building

> E.g. 0-1000,0-1000 is the root area split into

> NE: (0-500,0-500)

> NW:(500-1000,0-500)

> SE: (0-500, 500-1000)

> SW: (500-1000, 500-1000)

> This counts as one level

> For each of these nodes split again until we have reached the required number of levels

---

## Building

- We could just store all our nodes in one long array and rather than use pointers use index look ups

- To calculate the size of the array needed:

   - Each level of the tree has 4 times the number of nodes as the previous one

   - The first level has 1 (the root)

   - The second has 4

   - The third has 16

   - The fourth 64 etc.

---

## Node Again

> While it is possible to calculate a nodes bounding area when traversing the tree it is often faster and easier to just store the area in the node

typedef Node {

Vector2 boundingCoordinates[4]; // min, max in x and z

int ne, nw, se, sw; // indexes into the node array Bucket*entityBucket; int parent; // also helpful

};

---

## Inserting

- To insert entities into our built tree we start at the root and then:

   1. See if the entity is completely contained by the node region

   2. If it is loop to 1 with each child node until the entity no longer fits completely into the node region

   3. Add the entity to the bucket of the node that was the last ont to completely contain the entity

- With dynamic objects this will need to be carried out each time they move

- Note: advanced implementations may have entities to be sorted in the cell

## Search

- For collision use we could determine which entities to test by doing a search on a distance value

   - Example with entity centre p and distance 5

- If NE node is not empty

   - If (closest point from NE node is closer than 5 units)

      - Check for collision using the entities in this node and recurse with child nodes

- If NW node is not empty

   - If (closest point from NW node is closer than 5 units)

      - Check for collision using the entities in this node and recurse with child nodes

- If SE node is not empty

   - If (closest point from SE node is closer than 5 units)

      - Check for collision using the entities in this node and recurse with child nodes

- If SW node is not empty

   - If (closest point from SW node is closer than 5 units)

      - Check for collision using the entities in this node and recurse with child nodes

---

## Search

- Once we have determined the region of space, we wish to include in our search... e.g.

   - It could be a view frustum

   - It could be a fixed area (e.g. defined by an entities bounding circle / rectangle)

- ...we can use our tree to cull entities that are not in that region of space

- We do this by traversing the tree and ignoring all nodes whose regions do not cross the region in question

- We add all the entities found to a 'found list'

   - Again this is best as a fixed size array but alternatively you can just switch on or off a flag in the entity itself

- It is easy to forget to delete memory leading to leaks Windows will clean up after your program but if you are leaking regularly e.g., per level load, it can cause issues

- When you copy pointers to memory it is tricky to organise who is responsible for deleting them If you try to delete something twice you get a crash

## Smart Pointers

> Smart pointers are small objects that wrap the raw pointer alongside a count of how many times it has been shared

shared_ptr<Pointer> pnter;

> Pointer operations work the same as before

> Instead of

Entity *pnter = new Entity("Player");

> We write

shared_ptr<Entity> pnter= make_shared<Entity>("Player");
